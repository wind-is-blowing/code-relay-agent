# 项目定位、指标与工程取舍

整理日期：2026-10-31。当前实现、历史实验与后续设想分别说明；未开展新的微调训练。

## 1. 本地小模型定位与微调

推荐定位：**面向本地小模型与有限上下文/调用预算的长任务 Coding Agent**。
评测用 Qwen3.5-9B，产品曾用 4B；模型适配层支持兼容接口，因此不是只能调用本地模型。
“本地”描述部署位置，“小模型”描述规模，“资源受限”需要落到量化、上下文、请求次数、输出/时间预算；不泛指所有企业都资源不足。
本项目实际验证的是有限预算下的证据和执行机制，不承诺小模型达到大模型的一般能力。没有测量总拥有成本或能耗时，不写“成本降低多少”。

本地开放权重可做 LoRA/QLoRA，但可微调的关键是权重、许可证及训练工具支持，而不是本地推理本身；可训练不等于已经取得任务收益。
[PEFT 量化训练文档](https://huggingface.co/docs/peft/developer_guides/quantization)说明了低比特基座与可训练适配器的组合；[Unsloth Qwen3.5 指南](https://unsloth.ai/docs/models/qwen3.5/fine-tune)提供该模型家族训练与导出路径。
通常基于训练框架加载支持的原始/训练用量化权重，不把 Ollama 中现成的推理文件直接当作普通全参数训练模型。

### 值得做的实验，而非为了简历增加一个词

先从真实轨迹统计失败类型：非法 JSON、Schema 不符、参数值错误、错误工具、无效重试、错用旧证据、未验证即结束。
如果主要是 JSON 格式，先做约束解码、参数验证和有限修复重试。[Ollama 支持按 JSON Schema 约束结构化输出](https://docs.ollama.com/capabilities/structured-outputs)；实际应用还需验证当前工具调用协议与服务版本是否兼容，不能直接在现有循环上假定可无损替换。

微调更有价值的目标是：**给定任务、当前证据和失败反馈，输出语义正确的下一步动作**。例如编辑未匹配后读取候选原文，版本不符时重新读取，测试后文件又变更时重新验证。

可先整理数百到一两千条经过核验的工具决策样本，这是实验起点而非必须规模。保留正确工具/参数、错误后的恢复、无需工具直接回答与应停止的样本；按仓库、任务族划分训练/验证/测试，不能随机把同一失败的近似改写分到两边。
不把 SWE 测试答案、参考补丁或已作为独立测试的轨迹加入训练再宣称同一测试仍是留出集。

建议三组：A 原模型+现有提示；B 原模型+改进提示/约束解码/相同执行保护；C 同等工程控制+LoRA/QLoRA。固定模型大小、预算、工具、温度及测试集。
分别报告 JSON 可解析率、Schema 合法率、工具/参数语义正确率、错误恢复率、无效重复次数、任务通过率、Token 与时延，以及原能力是否退化。
仅格式提高而任务通过率没提高，也应如实报告。成功后再把数据集、训练配置、冻结测试及实测结果写进简历。

## 2. Hit@5、Recall@5 与完整 RAG

令某问题的标准相关片段集合为 G，检索前五条为 R。

- Hit@5 = 1（R 与 G 有交集）或 0（无交集），再对问题取平均。
- Recall@5 = |R∩G| / |G|，通常先逐题计算再做宏平均。
- 需要三个证据片段而只找到一个时：Hit=1，Recall=1/3。
- 每题只有一个相关片段且统计方式一致时，两个指标数值相同。
- 无答案题 G 为空，不能随意算作 Recall=0 或 1；单独统计证据拦截与错误接受。

单条文档可回答的问题用 Hit 直观；涉及规则、例外和操作前提的多证据问题，Recall 更能衡量证据完整性。二者都不能单独代表最终回答效果。还要看排序质量、来源/产品适用性、证据充分性、生成事实与引用正确性、澄清及完整任务结果。
[Haystack 文档](https://docs.haystack.deepset.ai/docs/documentrecallevaluator)同时描述了 single_hit 与 multi_hit 模式，报告必须写明实际定义，不能只照抄指标名。

项目旧 v3 写 Recall@5，但实现是至少命中一个，已更正为 Hit@5。22 条正例的 68.18%→86.36% 是项目词法 RRF→门控混合，不是相对外部框架。

## 3. 成熟对照与无答案拦截

项目已经有 Haystack 的 BM25、dense、RRF、固定 CrossEncoder 对照及消融，并非还没外部基线。
应同时保留“标准组件基线”和“自己系统关闭单个模块”的比较：前者比较方案竞争力，后者检查机制贡献。
公平比较固定资料、切块、模型、公开产品信息和预算；阈值在开发集定，冻结后在独立问题族测试。不能让己方看已确认产品而让基线猜，也不能把关闭过滤的消融叫作战胜 Haystack。
当前记录中纯向量在部分配置上很强，不能挑弱基线宣称全面优于成熟方案。

线上原生检索主要靠以下机制控制无答案返回：

1. 产品及地区/固件/有效期/发布状态等范围检查，缺失条件可能要求补充。
2. 从相关性词项中移除已知型号等低信息词，处理明确否定，避免只因提到了产品就返回任意资料。
3. 词法弱匹配过滤，例如仅正文单个弱二元词重叠不足以作为证据。
4. 真实向量通道有相似度门槛：已有词法候选与纯向量新增候选采用不同门槛，当前代码分别为 0.35 和默认 0.48。
5. 返回前复核当前发布版本/内容哈希；没有合格证据则返回 not_found/needs_info 等状态。

RRF 只融合排名，不保证某一条资料足够回答问题；相似度阈值也不等于答案概率。后续模型需求覆盖审核及引用核验属于离线实验，不能默认写成已上线机制。
“不返回证据率”不是“生成正确拒答率”，后者还要检查最终答复是否虚构结论。

## 4. 名称与项目分工

- **续码 Coding Agent｜本地小模型开发助手**：简介再突出长任务、有限预算，重点是版本证据与执行可靠性。
- **知维售后 Agent｜多产品消歧与证据检索**：重点是适用范围、证据充分性及人工接续。

名称为本次建议的展示名，未声明商标唯一性；运行模块名和接口没有改名。
Coding 保留恢复/记忆，但压缩成支撑能力；客服用“产品未确认→先消歧、证据不足→追问、升级前→确认”等具体触发条件，减少重复罗列状态机、幂等和恢复。
11 个工具、6 类策略只是规模。简历应写它们支持了哪条业务链、执行什么前提，而非用数量代替效果。

## 5. 18 个百分点是否不够吸引

本项目 17/50=34%，mini 8/50=16%。

- 绝对差：34%−16%=18 个百分点。
- 相对增幅：(34%−16%)/16%=112.5%。
- 比值：34%/16%=2.125，约 2.13 倍。

三个表达都正确，但比较条件和样本没有改变。推荐简历写“34% 对 16%，提升 18 个百分点”；若需要强调可补“约为基线 2.13 倍”，不单独用 112.5% 放大观感。
50 题每题一次，不能据此确认稳定性或泛化范围；17 题通过也意味着仍有 33 题未通过。

**主动结束**是运行控制指标：模型满足结束协议主动给出最终回复。
**补丁通过**是独立评分指标：停止时得到的补丁通过指定故障及回归测试。
模型先改对代码再耗尽预算，可能未主动结束但补丁通过；模型说完成但代码错误，则主动结束而补丁未通过。
简历主指标写解决率，运行状态放评测文档；当讨论稳定性/公平性时要主动解释。审计中主动结束为本项目 13/50、mini 0/50，而补丁通过为 17/50、8/50。

## 6. 预算内证据管理逐步解释

### 第一步：把一次观察变成有身份的记录

工具读、改、测完成后，记录证据 id、工具调用 id、文件路径、读取范围、文件完整 SHA、修改前后版本、退出码、测试数量及范围，并关联输出档案。SHA 前缀仅用于展示，执行检查保留完整哈希。
原始工具消息和档案受各自容量/完整性限制，不能承诺所有输出无限完整保存。

### 第二步：刷新当前有效性

组装上下文时重新核对文件版本，并根据工作区/环境指纹更新最近测试状态。
“先测试通过，后修改文件”会使旧测试不能作为当前交付证明；未运行任何测试也不能仅靠退出码 0 说验证通过。

### 第三步：在规则排序中挑候选

查询由当前目标和补充要求组成。当前确定性打分：文件路径/文件名命中加 100，每个有效关键词命中加 5。
候选排序键为“是否测试记录、相关性分数、是否失败、时间”，降序处理；还过滤无关记录并保留少量兜底项。
这是规则选择，不是训练排序器、向量检索或最优背包算法；排序中测试类别优先，时间是后面的排序因素，不能把它概括成只看最新记录。

### 第四步：先放卡片，再补原文

先保留任务阶段、验证状态、未完成操作数、省略条数和展开入口，再逐条加入卡片。每次按模型消息转换后的内容估算长度，超预算就撤回该卡片并继续尝试后面的记录。
剩余预算用于相关原文摘录，单条最多约 320 字符；尽量保留命中行的邻居和限定/否定条件。加摘录超预算就撤回摘录，不丢卡片。
过期文件的摘录默认不放进视图，防止小模型继续抄旧值。
700 是单独证据视图估算预算，不是精确 tokenizer 硬上限，也不包括整个对话、系统提示词和工具定义。

### 第五步：模型缺细节时显式回查

系统指导告诉模型：省略不等于不存在；已有有效事实足够时不要重跑工具。
`evidence(query=文件名或关键词)` 检索本分支证据目录；`evidence(id=编号, query=关键字)` 定位历史原文；`offset/limit` 用于分页。
展开先检查分支、工作区和版本，优先读取完整输出档案，必要时回退原工具消息；返回来源完整性。默认拒绝把过期文件展开为当前事实，要求重新 read；明确查历史时才允许 allow_stale。
长档案分页还可附任务相关的有界原文摘录，减少弱模型逐页扫描的无效往返。工具不重跑 Shell，也不调用额外摘要模型。
模型仍可能错误选择展开、反复分页；工程机制不保证它始终正确判断信息是否充足。

### 第六步：只折叠给模型看的副本

历史读/测输出在相应模式与压力条件下折叠为证据引用；当前工作集、最近工具配对等保留。原始分支历史和已归档结果不因这次投影视图而被直接改写。
语义摘要回答“之前做了什么”；证据层回答“依据来自哪里、针对哪个版本、现在是否仍有效、如何回查”。二者互补，摘要本身不自动验证文件版本。

### 一个具体例子

第一次读取 app.py 得到端口 8123，记录 SHA=A。文件后来变成 SHA=B，端口变为 9017。
旧摘要可能仍写 8123。证据层发现 A≠B，标记旧记录过期、隐藏旧摘录；模型必须重新 read 才能回答当前端口。
若文件未变且历史证据已足够，就直接复用；需要详情则展开档案，不必重新执行原命令。

### 推荐简历表述

为读文件、修改与测试结果记录来源及文件版本，设计预算内选择与按需展开，在约 700 Token 的证据区内保留关键记录，版本失效时要求重新取证；在 10 类场景、20 组配对决策测试中，正确数由 17/20 提升至 20/20，累计输入 Token 减少 58%。

## 7. 可靠性为什么用真实失败解释

真实 xarray 失败由精确编辑不匹配引发，模型后来将单函数片段覆盖为整个模块。原子写入照样可以完整提交错误内容。
修复重点是候选原文诊断、覆盖保护，并以原错误参数回放验证会拒绝破坏性修改；同题模型修复仍失败，保留负结果。
SHA 检查版本，幂等记录约束已知文件修改的重复执行，原子替换防止半份文件；它们不保证任意 Shell/远端副作用恰好一次，也不证明新代码逻辑正确。
